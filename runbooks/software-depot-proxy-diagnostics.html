VCF 9.1.x · Customer troubleshooting

Is the proxy blocking the Software Depot?

A read-only investigation that connects a failed depot request to the customer proxy’s access logs and allowlist.

Draft · validate against your release

Goal: identify the time, originating runtime, destination and response for a failed depot request, then correlate it with the proxy decision. A proxy denial is evidence of a policy problem; a download failure alone is not.

Scope: connected Software Depot on VCF 9.1.x using a customer outbound proxy. A bastion or VCF Download Tool has its own proxy configuration and requires separate logs.

Before you begin

Use an authorized, read-only shell and Kubernetes context for the VCF services runtime hosting the affected depot. Do not use a Supervisor or workload-cluster context by mistake. Broadcom KB 453506 documents the depot namespace, pod prefix and download-service container for VCF 9.1. Confirm the deployed version and names before use: this procedure has not yet been validated on the lab’s 9.1.1 runtime. If SSH is disabled, enabling it is a separate configuration change.

Logs can contain credentials, tokens, signed URLs or customer information. Review them locally; sanitize before sharing. Do not print environment variables, proxy credentials, configuration secrets or raw API responses.

01 · Establish the failure

Record the context

In VCF Operations, identify the affected Software Depot and its connection mode. Where available, start with Operate → Logs. For direct access, identify the affected services runtime control-plane node under Build → Lifecycle → VCF Management → Components → VCF services runtime → Nodes and use the customer’s authorized administrator and documented SSH procedure. Record the VCF version, affected runtime instance, failing action, approximate time and time zone. Ask the proxy team for the proxy endpoint and the runtime’s actual egress source IP or addresses as observed by the proxy. A runtime can have multiple source IPs.

Do not trigger a new download just to capture logs unless the customer authorizes a bounded test. Use an existing failure window first.

02 · Identify the workload

Verify context and locate the depot pod

In the approved runtime context, run:

kubectl config current-context
kubectl get namespaces
kubectl -n vcf-fleet-depot get pods -o wide

Confirm the context and namespace with the administrator. If the namespace does not exist, stop and obtain the release-specific supported path. Select the relevant depot pod from the output and list container names only:

kubectl -n vcf-fleet-depot get pod <depot-pod> \
  -o jsonpath='{.spec.containers[*].name}{"\n"}'

Broadcom KB 453506 identifies the pod as depot-service-<suffix> and the download-service container for VCF 9.1. Confirm both appear in your deployment; do not substitute the file-server, gateway or registry container.

03 · Inspect the failure window

Review the depot container logs

Replace the placeholder with the verified depot-service pod. The download-service container is documented for VCF 9.1; verify it is present for your build. The time window below is an example; choose a short window around the failure. Review output in the customer's secure terminal.

kubectl -n vcf-fleet-depot logs <depot-pod> \
  -c download-service --since=30m --timestamps | less

In less, search for /proxy, /403, /407, /timeout, /certificate, or the destination hostname; press n for the next match and q to exit. If the container restarted, repeat with --previous; previous logs may be unavailable.

Record only the timestamp, destination hostname and port, sanitized error class, and any request ID. A line mentioning an HTTP status does not by itself establish which intermediary returned it. In a support bundle, KB 453215 identifies vcf-fleet-depot/<node_name>/depot-service-<identifier>/download-service/console-log; this is a bundle location, not a verified live filesystem path.

04 · Correlate

Ask the proxy team to check its access logs

Provide the failure window and time zone, observed runtime source IP, destination host and port, and request ID if available. Ask for the proxy’s policy decision, authentication outcome and any redirect or additional destination. Compare the proxy timestamp and source IP with the depot event; the proxy logs are the strongest evidence of an allowlist denial.

ObservationWhat to check next
Proxy log shows deny / policy ruleIdentify the exact destination, port, source and rule; ask the proxy owner to evaluate the allowlist.
407 Proxy Authentication RequiredCheck proxy authentication configuration and the proxy log. Do not expose or rotate credentials as part of diagnosis.
403 ForbiddenIdentify whether the response came from the proxy or upstream and inspect the matching proxy decision; 403 alone does not prove an allowlist block.
Certificate or trust failureCheck the certificate chain and whether TLS interception requires the proxy CA in the depot truststore. Use the release-specific Broadcom procedure.
Timeout / no matching proxy recordCheck the source IP, time window, DNS, routing, firewall and whether the runtime is actually using the proxy. Absence in a log is not proof of direct egress.
Upstream 401 or 404Investigate upstream entitlement, credentials or artifact availability; do not assume the proxy is responsible.
05 · Destinations

Compare with the vendor list

For VCF 9.1.x, Broadcom lists dl.broadcom.com, eapi.broadcom.com, vvs.broadcom.com and vsanhealth.vmware.com for binary downloads, and vcf.packages.broadcom.com from 9.1.1. Supervisor and VCF service downloads also list projects.packages.broadcom.com. The listed destination port is 443.

Use the current vendor list for the exact release and enabled features. This is not a complete firewall allowlist; CDN redirects and the proxy’s policy model may require further investigation. PAIS mirroring and bastion tools have separate source and proxy paths.

06 · Confirm

Validate the fix with the proxy owner

Once the customer approves any proxy change, repeat one agreed, bounded operation and correlate the depot result with an allow decision in the proxy logs. Record the destination, source, timestamp, rule and outcome. Do not turn off TLS validation or bypass the proxy to make the test pass.
